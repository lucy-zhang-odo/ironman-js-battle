# Day 21 四個 bug 的答案(找完再看!)

## Bug 1:清除紀錄按鈕壞掉【大聲失敗】

**重現**:點「清除紀錄」按鈕
**現象**:紀錄文字沒有變回「尚無」,Console 出現紅字
**錯誤訊息**:`Uncaught ReferenceError: showRecrod is not defined`
**原因**:函式名稱打錯字,`showRecord` 寫成 `showRecrod`

```js
showRecrod();     // ← 少了一個 o、順序顛倒
```

**注意一個細節**:紀錄其實**真的被刪掉了**(`removeItem` 那行有跑),只是畫面沒更新。因為錯誤發生在下一行,前面的程式照樣執行 —— 這是 Day 9 學的「執行期錯誤從出錯那行開始砍掉後面」。所以重新整理頁面會發現紀錄真的不見了。

**這個 bug 的可怕之處**:如果不看 Console,會以為「刪除功能壞掉」,實際上是「刪掉了但沒告訴你」。

## Bug 2:小怪太早變紅【安靜失敗】

**重現**:攻擊到小怪剩 30 血以下
**現象**:血量字變紅色的時機不對 —— 小怪滿血 60,照設計應該剩 18(30%)才變紅,實際上剩 30 左右就變了
**原因**:複製貼上時用錯物件

```js
if (state.enemy.hp <= state.hero.maxHp * 0.3 && ...)
//                        ^^^^ 應該是 state.enemy.maxHp
```

`hero.maxHp` 是 100,所以門檻變成 30 而不是 18。

**為什麼難發現**:它**看起來完全正常**,只是時機早了一點。除非你算過 60 × 0.3 = 18,否則根本不會懷疑。這種「用錯物件但型別正確」的 bug 不會報錯,是複製貼上最典型的後遺症。

## Bug 3:紀錄越來越差【安靜失敗,需要玩很多次】

**重現**:打贏好幾場,觀察「最少回合紀錄」
**現象**:紀錄數字**越來越大**,而且每次打贏都說「新紀錄!」
**原因**:比較方向寫反

```js
if (best === null || turns > best) {   // ← 應該是 turns < best
```

現在的邏輯是「花更多回合才算破紀錄」,完全相反。

**為什麼難發現**:
- 第一次玩一定會存,看起來正常
- 要玩好幾場、而且回合數剛好有高有低,才看得出趨勢
- 文字還會很開心地說「新紀錄!」,誤導你以為是對的

**這正是 QA 最該抓的那類 bug**:單次操作看不出來,要累積觀察才會發現。跟 Day 16 的亂數統計是同一種思路。

## Bug 4:再戰之後第一擊就變鞭屍【安靜失敗,特定條件】

**重現**:打贏小怪 → 按「再戰一次」→ 按「攻擊」
**現象**:血量是滿的、按鈕寫著「攻擊!」,但按下去卻顯示「請不要對小怪屍體動手!」
**原因**:`reset()` 忘記重置 `state.isOver`

```js
function reset() {
  state.hero.hp   = state.hero.maxHp;
  state.enemy.hp  = state.enemy.maxHp;
  state.turn      = 1;
  state.whipCount = 0;
  // state.isOver = false;   ← 少了這行
```

**為什麼難發現**:平常玩不會遇到 —— 你得先打贏、再按再戰、再攻擊,三個動作都做才會出現。而且**畫面看起來一切正常**(血滿的、按鈕是攻擊),只有行為不對。

**這個 bug 的意義**:它正是 Day 18 導入 `state` 物件時擔心的事 —— 狀態變多之後,**重置時很容易漏掉某一項**。狀態集中在一個物件裡有幫助,但不會自動解決這個問題;真正的解法是「重置時對照 state 的每一個欄位檢查一遍」。

## 四個 bug 的分佈(這是重點)

| Bug | 類型 | 會不會報錯 | 難度 | 對應的真實情境 |
|---|---|---|---|---|
| 1 打錯函式名 | 大聲 | 會 | 低 | 開發時自己就會發現 |
| 2 用錯物件 | 安靜 | 不會 | 中 | 複製貼上的後遺症 |
| 3 比較寫反 | 安靜 | 不會 | 高 | 要累積多次觀察才看得出 |
| 4 漏重置狀態 | 安靜 | 不會 | 高 | 特定操作順序才觸發 |

**四個裡面有三個不報錯。** 這就是為什麼「只要沒有紅字就代表沒問題」是錯的,也是為什麼軟體需要測試。

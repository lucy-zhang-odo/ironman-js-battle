# Day 26:開場與結果——讓玩家知道怎麼玩、知道發生了什麼

## 這天做了三件事

### 1. 修掉「沒出征也能打」

你自己發現的問題:畫面上寫著「請先輸入名字,然後按下出征!」,但**不照做也能直接攻擊**。

這是**規格與實作不一致** —— 文字說必填,程式沒擋。這種問題在測試裡很常見,而且比純粹的 bug 更麻煩,因為要先決定「哪一邊才是對的」。

我選擇讓程式遵守文字(而不是改文字):

```js
if (!state.ready) {
  addLog("請先輸入勇者名字,並按下「出征!」", "log-warning");
  nameInput.focus();
  return;
}
```

注意這裡沿用 Day 25 的原則:**擋下來,並且說明原因**。而且順手用 `focus()` 把游標移到該填的地方 —— 不只告訴玩家哪裡錯,還帶他過去。

### 2. 加遊戲說明

用 HTML 原生的 `<details>`:

```html
<details id="howto">
  <summary>怎麼玩?</summary>
  <ul>...</ul>
</details>
```

`<details>` + `<summary>` 是瀏覽器內建的摺疊區塊,**點一下就會展開,完全不需要 JavaScript**。想看的人點開,不想看的人不會被佔版面。

說明內容涵蓋:操作方式、一回合發生什麼事、傷害有浮動、血條變紅的時機、目標是什麼、勇者會死。

### 3. 結果橫幅

原本勝負只有紀錄裡一行字,很容易滑過去。現在會出現一塊明顯的橫幅,勝利綠色、失敗紅色。

用 `hidden` 屬性控制顯示:

```js
resultBox.hidden = false;   // 出現
resultBox.hidden = true;    // 藏起來
```

`hidden` 是 HTML 的標準屬性,比自己寫 `style.display = "none"` 更語意化 —— 而且螢幕閱讀器也看得懂。

**刻意不做成蓋住畫面的彈窗**,因為那樣就按不到鞭屍了。

## 為什麼「遊戲說明」值得單獨花時間做

這是 Day 21 最重要的那個結論的延伸:

> **一個 bug 要能被「發現」,前提是有人知道「正確的行為應該是什麼」。**

當時你自己說過:血量變紅那個 bug,對一般玩家來說最難發現,因為「沒有遊戲說明,玩家不知道遊戲機制,不會覺得有問題」。

現在說明裡明確寫了「血量低於三成時,血條會變紅」。這句話同時是兩件事:

1. **給玩家的**:知道該注意什麼
2. **給測試的**:一條可以驗證的規格

沒有這句話,那個 bug 可以活到永遠。

## 你要做的測試

1. **沒填名字直接按攻擊** → 應該被擋,而且游標會跳到輸入框
2. **打完一場** → 結果橫幅出現,顏色對不對?
3. **打贏後按鞭屍** → 橫幅還在,鞭屍照樣能按?
4. **按再戰一次** → 橫幅消失,而且**不用重新出征**就能打
5. **展開/收合遊戲說明** → 版面會不會跳動?
6. 讀一次說明:**有沒有哪條規則是錯的,或是漏掉的?**

## 今天的原創填空點

1. **「規格與實作不一致」時,你會改哪一邊?** 這次我選了「讓程式遵守文字」,但反過來(改成「名字選填」)也說得通。你的判斷標準是什麼?
2. **再戰一次要不要重新出征?** 我選擇不用(`ready` 不重置)。你覺得呢?
3. **第 6 題**:你讀說明時有沒有發現漏掉的規則?那個「漏掉」本身就是文章素材 —— 因為**寫說明會逼你把隱含的規則講出來**。

# Day 21:除錯——用 QA 的方法抓 bug

這天不學新語法,學的是**怎麼找出問題**。而且這是整個系列最貼近你本業的一天。

## 一、兩種失敗:大聲的和安靜的

| | 大聲失敗 | 安靜失敗 |
|---|---|---|
| 例子 | 404、SyntaxError、TypeError | 功能沒生效、資料算錯、畫面沒更新 |
| 使用者看得到嗎 | 看得到(畫面壞掉、出現錯誤代號) | **看不到**,一切看起來正常 |
| 誰會回報 | 所有人 | 幾乎沒有人 |
| 好不好查 | 錯誤訊息會告訴你檔名和行號 | **沒有任何線索** |

我們一路累積的安靜失敗清單(速查表裡有):
- 字串 `s[0] = "明"` 不報錯也不生效
- 兩個同名函式安靜覆蓋
- 遮蔽留下的 `undefined`
- `addEventListener("click", attack())` 掛上 undefined
- 資料改了但畫面沒更新
- 使用者輸入的標籤被解析
- 忘記 `clearInterval` 的計時器在背景永遠跑
- 亂數少了 `+1`,最大值永遠不出現

**這才是真正需要 QA 的地方。** 大聲失敗開發者自己就會發現,安靜失敗要有人去測才找得到。

## 二、除錯的三個工具

### 1. `console.log` — 最常用

但有分等級:

```js
console.log("一般訊息");
console.warn("警告");      // 黃色
console.error("錯誤");     // 紅色
console.table(陣列或物件);  // 表格化,看資料超好用
console.count("進來幾次");  // 自動計數,不用自己加變數
```

`console.table` 和 `console.count` 今天一定要試,尤其 `console.table` 看陣列資料非常清楚。

### 2. 中斷點(breakpoint)— 讓程式停下來

比 `console.log` 強的地方:**不用改程式碼,而且可以看當下所有變數**。

步驟:
1. F12 → **原始碼(Sources)** 分頁
2. 左側找到你的 `.html` 檔,點開
3. **點一下行號** → 出現藍色標記 = 中斷點
4. 操作網頁,程式跑到那一行就會停住
5. 右側可以看到當下每個變數的值
6. 上方按鈕控制:
   - ▶ 繼續執行
   - ⤵ 跳過這一行(Step over)
   - ↓ 進入函式內部(Step into)

**中斷點最適合用在**:「我不知道是哪個變數不對」的時候。`console.log` 適合「我猜是這個變數,印出來看看」。

### 3. `debugger` 陳述句

在程式裡寫一行 `debugger;`,只要 DevTools 開著,執行到那裡就會自動停下來 —— 等於用程式碼設中斷點。

```js
function attack() {
  debugger;      // 每次攻擊都會停在這裡
  ...
}
```

## 三、QA 的除錯思路(這是你的主場)

工具只是手段,真正重要的是方法。你平常做的事其實就是:

1. **縮小範圍**:問題發生在哪一步?輸入時?計算時?顯示時?
2. **找出重現步驟**:什麼條件下一定會發生?
3. **對照正常情況**:同樣的操作,換個輸入還會壞嗎?
4. **一次只改一個變因**:不然修好了也不知道是哪個原因

第 4 點在寫程式時特別重要 —— 一次改三個地方,壞了不知道是誰害的。

## 練習說明

`day21.html` 是一個**故意寫壞的版本**,裡面藏了 4 個 bug。

規則:
- **先不要看程式碼找答案**,像測產品一樣先操作看看
- 用 DevTools 找出每個 bug
- 記錄下來:什麼操作 → 什麼現象 → 你猜的原因

四個 bug 的難度:
1. 一個是**大聲失敗**(有錯誤訊息)
2. 三個是**安靜失敗**(不報錯,但行為不對)

提示:有一個 bug 只有在「特定條件」下才出現,平常玩不會遇到 —— 這是最像真實世界的那種。

找到幾個都可以,找不到也沒關係,過程本身就是文章素材。答案在 `答案.md`(先別偷看!)。
